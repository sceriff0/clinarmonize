§0What this is, and the one thing it is built around

clinarmonize lifts 1..N clinical cohorts into an OMOP CDM subset that is defined at runtime by a concept pack, not by the pipeline's own source. A reader coming to the repo cold sees ten Nextflow processes and thirty parameters and reasonably assumes the point is the mapping. It is not. The mapping is the easy half.

Outcome-Blind Mapping

No harmonization decision — column match, value mapping, unit conversion, endpoint derivation, or linkage threshold — may be a function of the outcome variable. Every structural oddity in the graph below exists to make that testable rather than merely asserted.

The outcome variable is never a column name in this codebase. It is whatever the pack flags outcome: true (subworkflows/local/ingest/main.nf:110-113 refuses a pack that flags none), which is what lets one invariant test defend an oncology run and a critical-care run without a line of code changing.

Read this alongside

p-harmonize.html is the design plan — eighteen sections of intent, contracts, and rulings written before and during the build. This document is the as-built counterpart: it describes only code that exists in the working tree today, and every number in it was read out of a file rather than out of the plan.

§1The nine-stage graph — and the gate that says which four exist

The pipeline declares nine stages. Four are built. The interesting part is which four: the built set is deliberately not a prefix.

That gap is why the gate checks the requested stage's own membership rather than walking the graph for the first hole. A contiguity check would refuse --stop_after propose over a hole that nothing downstream of it reads — propose consumes per-dataset profiles directly, never anything link would have produced — while still correctly refusing --stop_after link itself (workflows/harmonize.nf:36-60).

Refusal 1 — unbuilt stage

Any --stop_after naming a stage outside the built four aborts with the list of what is built. A run that reached the end without the stage having happened would be a silent success, which is the failure mode this gate exists to prevent.

The one exemption

The invariant harness may pass the gate — but only when the requested stage equals --invariant_scope (harmonize.nf:563). The harness's measurement is which contract output an unbuilt stage failed to produce, so refusing it would replace the finding with the refusal. Nothing becomes silent: the report names every replicate that produced no ledger and withholds the verdict proof.

§3Inputs and the contracts they must satisfy

§3.1The two-level samplesheet

Five columns, all required. holdout has no default — assets/schema_input.json rejects a sheet that omits the column rather than assuming false, because assuming false silently unseals data.

ColumnTypeConstraint
cohort_idstringrequired, no spaces; carried into meta
dataset_idstringrequired, no spaces; carried into meta
roleenumclinical · treatment · biopsy · imaging · other
pathpathrequired; must point at an existing file
holdoutbooleanrequired, true/false; a missing column is a rejected sheet
Refusal 2 — duplicate dataset

A repeated (cohort_id, dataset_id) aborts before anything is written, naming every offending row number (subworkflows/local/ingest/main.nf:31-47). The check runs before params_hash.txt is written, so a rejected sheet leaves no trace at all.

§3.2The concept pack — the pipeline's target variable set

The pack is what makes this a general harmonizer rather than a study-specific script: the set of variables to map to is data, supplied at runtime, never source. Four top-level keys are mandatory (pack, version, vocabulary, variables), and each variable must carry name and domain; domain: derived then requires derivation, and every other domain requires concept_id and type (ingest/main.nf:64-107).

assets/packs/minimal.yaml — the default pack, in full

pack: minimal-generic
version: 0.1.0
vocabulary: athena-2026-08 # pinned release; hashed
variables:
  - name: age_at_index
    domain: person
    concept_id: 0
    type: continuous
  - name: sex
    domain: person
    concept_id: 0
    type: nominal
    domain_values: [male, female, other, unknown]
  - name: vital_status
    domain: observation
    concept_id: 0
    type: nominal
    domain_values: [alive, dead, unknown]
  - name: time_to_event
    domain: derived
    derivation: survival_time
    unit: day
    outcome: true # excluded from EVERY channel
Refusal 3 — a pack with no outcome

A pack where no variable carries outcome: true is rejected outright (ingest/main.nf:110-113). Without that flag the invariant has nothing to be an invariant about, and the permutation harness would silently certify a run in which it permuted nothing.

The pack is hashed (sha256 of its bytes, ingest/main.nf:141) and the hash travels on ch_pack. A relative --concept_pack resolves against projectDir, not the launch directory — nf-test launches from its own sandbox, and file() would otherwise silently resolve the default to a path that does not exist (ingest/main.nf:122-131).

Result 1 — --channel_weights is not what gets applied

You configured value: 0.30. No candidate in this run was ever scored with a weight of 0.30. Channels that cannot score are dropped and the remaining weights are renormalised per candidate:

For AGE_AT_DX only 0.15 + 0.15 + 0.10 = 0.40 of configured weight could score, so each survivor is divided by 0.40: 0.15/0.40 = 0.375, 0.10/0.40 = 0.250. For SEX four channels scored, summing 0.70: 0.30/0.70 = 0.4286. The weight a channel actually carries depends on which other channels happened to be scoreable for that candidate. Tuning --channel_weights without knowing that will not do what you expect.

Result 2 — two of the six channels never scored anything, all run

ChannelStatus in this runReason, from detail
unit_plausibility0 of 5 candidates scored"variable declares no unit" — in the minimal pack only time_to_event has a unit, and it is outcome-excluded
distribution_distance0 of 5 candidates scored"no CONFIRMED columns exist" — it compares against previously confirmed mappings, and on a first run there are none
The bootstrapping trap

distribution_distance cannot contribute to the first run of any study, because its reference set is what earlier runs confirmed. 30% of the configured weight (dist 0.15 + unit 0.15) is inert here, and the pipeline reports this honestly in the detail column rather than scoring 0.0 and dragging every total down — a distinction that matters, since a 0.0 score and an unscoreable channel mean opposite things.

Result 3 — the name algorithm changes between stages

AGE_AT_DX → age_at_index scored 0.30 at the generator and 0.95 at the channel. Both are correct: the generator uses character-trigram Jaccard (bin/propose_candidates.py:75-81) to decide whether to propose at all; the channel uses Jaro-Winkler to decide how good the proposal is. Two different algorithms with the word "name" in both. Do not compare the numbers.

The inversion: SEX scores 0.5, gender scores 0.6071

SEX → sex is a perfect name match (1.00). gender → sex is a name match of 0.50. The worse-named column wins, because SEX's values are M/F — Jaccard 0.0 against the pack's [male, female, other, unknown] — while gender's are male/female, Jaccard 0.5. value_overlap carries an effective 0.4286, twice any other live channel, so a zero there is decisive.

This is the weight configuration working exactly as specified, producing a ranking a human would not have guessed. It is also the case for the confirmation plot: the reviewer needs to see that SEX's low score is a value-encoding problem, not a wrong mapping.

The arithmetic is checkable by hand, which is the point of publishing effective_weight:

Why, and why it matters more than the hash

The harness permutes a column only when its header canonicalises — lowercase, keep alphanumerics only (bin/permute_outcome.py:43-47) — to the pack's outcome variable name:

CohortColumncanonical()TargetPermuted?
COHORT_AOS_DAYSosdaystimetoeventno

COHORT_A was never perturbed, so its half of the identical hashes proves nothing at all. Reporting proof here would have been a false clearance — and note that the n_distinct_hashes == 1 test on its own would have issued one. The guard is what stands between a green tick and a vacuous one.

Had that guard passed, insufficient-permutations was waiting behind it: 10 ran, --invariant_n_permutations requires 100.

Two fixes make this study certifiable, and neither is a threshold change: rename COHORT_A's OS_DAYS to the pack's own outcome name at ingest, or give the pack an alias mechanism so one variable can answer to several source headers.

What five rules actually buy you

22 columns were profiled. 5 became rules. Of the 17 that did not: 3 are the outcome columns the pipeline refuses to touch, 2 are age columns nothing matched, and the remaining 12 are identifiers, treatment lines, biopsy grades and imaging fields the minimal pack has no variable for at all. Coverage is a function of the pack, not of the pipeline — and measuring that gap is the unbuilt coverage stage's whole job.

Nothing applies those five rules. COHORT_A's clinical, treatment and biopsy tables are never joined; COHORT_A and COHORT_B are never unioned. The deliverable at the end of this example is a reviewed, hash-pinned mapping specification — not harmonized data.

§4The holdout seal — the filter that has to happen early

A dataset marked holdout: true never reaches a process. Not "is ignored by" — never reaches. The filter sits at channel construction, upstream of anything that would stage a file into a work directory.

// workflows/harmonize.nf:526
def ch_open = INGEST.out.datasets.filter { meta, _table -> HoldoutPolicy_admit(meta, lock) }

A filter inside a process that reads the table would be decoration: by the time the script runs, Nextflow has already copied the file into the work directory. Because the seal is a channel property, it is also a DAG property — a leaked row would show up in .nextflow.log as a submitted task, so the seal is verifiable from the execution trace and not only from an assertion about channel contents.

§4.1Unsealing is a four-way match, not a flag

--unseal alone does nothing. resolveHoldoutLock() (harmonize.nf:148-189) refuses the run unless all four hold:

  1. locked_model.json exists at --locked_model and parses as JSON.
  2. Its covers list contains every requested dataset id.
  3. Its params_hash equals this run's params hash.
  4. Its analysis_git_sha equals git rev-parse HEAD of the pipeline about to run.

The params hash is deliberately narrow — sha256 over exactly input, the resolved concept-pack path, and allow_single_dataset (harmonize.nf:91-98). It excludes the unsealing params themselves, because a "lock this analysis" run never sets them and the later "check against the lock" run always does — including them would make every lock unmatched by construction. It also excludes output-location params, which change where a run reports, not what it computes.

Refusals 4–7 — the four lock checks

Each failure names the mismatch and ends with the same clause: "No held-out dataset was admitted; unseal.log is unchanged." On success the log is appended before the first held-out row is admitted, so the audit trail cannot lag the admission it records.

Nextflow's own workflow.commitId is not used for check 4: it is only populated for a pulled, versioned pipeline (nextflow run org/pipe -r v1.0), never for the plain local-directory run this pipeline is actually executed as (harmonize.nf:currentGitSha).

§5Profile — one evidence record per column

Everything that is a pure function of one table's bytes happens in PROFILE_COLUMNS; everything that is a property of the whole run happens in MANIFEST_PROFILING_FAILURES. The split is not stylistic — a single dataset's failure rate is not the run's failure rate.

FieldWhat it recordsKnob

inferred_typeint · float · bool · date · str · emptydate_formats

Why "in row order" matters

example_values being row-ordered is what makes a within-column shuffle observable at all (bin/profile_columns.py:290). A harness that reused the baseline profiles would be comparing a run against itself and would report "no leak" forever — which is why §6 re-profiles every permuted replicate rather than caching.

§5.1Unit inference, and what it will not claim

A header matching a pattern in assets/unit_patterns.yaml yields a UCUM candidate at that pattern's own confidence. Failing that, and only when --infer_unit_from_range is on, the value range yields a candidate at a fixed confidence of 0.3: a 0..1 or 0..100 range suggests a proportion, a 0..60 range suggests the ambiguous day/month pair (bin/profile_columns.py:150-165). The 0.3 is the point — a range-derived unit is evidence, never a decision.

§5.2Failure is counted, not swallowed

Three failure reasons exist: encoding, mixed_type, and unreadable, each carrying up to --fail_sample_k offending values (bin/profile_columns.py:238, 252, 300). Per-dataset failure files are not published — only the collated profiles/_failed.json is (conf/modules.config:25-36).

Refusal 8 — too much of the run failed to profile

frac = total_failed / total_columns; the run exits non-zero when frac > --max_failed_frac (default 0.05, bin/manifest_profiling_failures.py:47-52). It is a strict inequality over the run's columns, so one pathological dataset among twenty does not stop a run, and a systematically broken encoding does.

§6The invariant harness — the branch that only exists to try to fail

Set --permute_outcome_seed and the pipeline grows a second, parallel population of replicates. Every one of them travels the identical code path the real run uses. If the proposal ledger moves, something read the outcome.

§6.1Four structural choices, each load-bearing

  1. 1A shuffle, not a rewrite

    What

    The outcome column is permuted within each cohort, preserving its multiset exactly. Type, cardinality, value set, and every quantile are unchanged; only the row-level pairing between the outcome and every other column is destroyed (bin/permute_outcome.py:11-16).

    Why

    That pairing is precisely the signal an outcome-aware channel would be reading. A ledger that moves under this shuffle moved because something read the joint distribution — there is no other explanation left.

  2. 2An alias, not a second module

    What

    PROFILE_COLUMNS_PERMUTED is a DSL2 alias of PROFILE_COLUMNS, not a purpose-built test process (harmonize.nf:20).

    Trap

    A "profile for the test" module would be a code path the invariant was never actually tested on. The alias exists only because DSL2 permits one invocation per process name and the baseline still needs its own.

  3. 3The replicate id travels in the filename

    What

    PERMUTE_OUTCOME emits <prefix>.p<seed>.csv; the workflow reads the seed back off the name with a regex and fails loudly on a non-matching file (harmonize.nf:663-671).

    Why

    A process emits files, not structured records. The name is the only channel through which a per-file attribute can cross that boundary.

  4. 4N replicates in one execution, not N executions

    What

    The loop runs inside a single Nextflow run as N branches, rather than as a shell loop around N runs.

    Consequence

    100 permutations cost one JVM startup instead of 100 — the difference between a test that runs on every push and a test that moves to a nightly and then to nobody.

§6.2The verdict ladder

Eight verdicts, evaluated in this order. Only the first two lines below are good news; the point of the other six is that a failing run says why, not only how much (bin/invariant_report.py:172-187).

#VerdictFires when
1no-outcome-columna cohort carries no column matching the pack's outcome variable — every permutation was a no-op
2marginal-moveda permuted column's marginal changed; the shuffle did more than shuffle
3incomplete-permutationa cohort is missing replicates other cohorts have
4no-op-permutationevery seed produced the identical ordering for some column
5no-ledgera replicate produced no ledger.proposed.yaml to hash
6insufficient-permutationsfewer than --invariant_n_permutations ran
7proofall of the above cleared and exactly one distinct ledger hash
8leakmore than one distinct hash
Why the guards come before the count

Zero distinct hashes is not one distinct hash. If nothing was permuted, or nothing produced a ledger, then n_distinct_hashes == 1 follows trivially and would certify a vacuous run as a proof. Each guard above exists to make one specific vacuity impossible to mistake for evidence. There is no "mostly agree" — the verdict is proof or it is not.

The report lands at tests/invariant/report.json — outside --outdir on purpose (conf/modules.config:123-134): it is a statement about the pipeline's code, not an output of any one run's data. Ledger hashes are computed in Groovy straight off the channel rather than staged into the process, because all 100 ledgers share one filename by contract and staging them would force a rename that loses the only thing the report needs them keyed by (harmonize.nf:875).

§7Propose — three processes, one task per replicate each

Propose is where a column becomes a candidate mapping and a candidate gets a score. It is also the only stage the invariant claim is currently held over, which constrains everything in it: it must be a pure function of the profiles, and its output must be byte-stable.

§7.1PROPOSE_CANDIDATES — recall, capped

Cheap generators propose (column → variable) pairs; three are enabled by default — name_ngram, value_set, unit. A column with zero candidates is still emitted, with a null concept_id: silence and "nothing matched" are different facts and the ledger distinguishes them.

The invariant, enforced structurally

Outcome-flagged variables are filtered out of the candidate variable set before a single generator runs (bin/propose_candidates.py:227). Nothing downstream can propose a mapping to the outcome, so nothing downstream can be a function of it. §7.2 then re-asserts this at its own boundary rather than trusting the caller.

--max_candidates_per_column (default 20) is a recall ceiling on distinct variables per column. Variables past the cut are not dropped in silence: they are counted into excluded_candidates and carried into the ledger, so a reviewer can see that a truncation happened (bin/propose_candidates.py:135-154).

§7.2PROPOSE_CHANNELS — six independent opinions

Each candidate is scored on six channels, weighted into one combined score. The weights are the pipeline's clearest statement of what it believes evidence is: value overlap is worth twice any other single channel.

ChannelKeyDefault weight
value_overlapvalue0.30
name_similarityname0.15
type_agreementtype0.15
distribution_distancedist0.15
unit_plausibilityunit0.15
cardinalitycard0.10

Weights come from --channel_weights (nextflow.config:50); which channels run at all comes from --enabled_channels (:51). unit_plausibility tries the conversions listed in --unit_factor_candidates — [1, 30.4375, 365.25, 0.001, 1000], i.e. identity, days-per-month, days-per-year, and the two metric decades (:52).

With --emit_confirmation_plots on (the default), the stage also writes one SVG per candidate: the one plot that would kill this proposal. That framing is deliberate — a plot chosen to confirm is decoration; a plot chosen to falsify is evidence a reviewer can act on in seconds.

§7.3PROPOSE_LEDGER — ordered so it can be hashed

Proposals are sorted by descending combined score, ties broken by variable name (bin/propose_ledger.py:144); the top --ledger_top_k (default 5) are written per column and the rest are counted, not listed (:155). Floats are rounded to --ledger_float_precision (default 4) so a float's last bit cannot change the file's hash (:79), and YAML is dumped with sort_keys=False over an explicitly ordered structure, so key order is a property of the code rather than of the serialiser (:179-184).

Why all this determinism theatre

The invariant test is sha256(ledger.proposed.yaml) compared across 100 runs. Any nondeterminism anywhere in propose — dict ordering, float noise, an unstable sort — would produce differing hashes and be reported as leak. The rounding and the fixed key order exist so that a leak verdict means what it says.

§8Confirm & compile — the gate that cannot be automated away

The pipeline will not map anything on its own recognisance. Between a proposal and a rule sits a file a human wrote.

Refusal 9 — no confirmed ledger

--confirmed_ledger defaults to null in every profile, -profile test included (nextflow.config:66). There is no auto_confirm flag, no score threshold, and nothing else anywhere in the CLI that can supply a decision. The only thing that makes this gate open is a real file on disk.

The refusal is a .subscribe on the baseline ledger channel, not an eager error() (harmonize.nf:804-814). DSL2 executes the whole workflow script top-to-bottom to build the graph before any task is scheduled, so an eager refusal fired before PROPOSE_LEDGER had run — and pointed the user at a ledger.proposed.yaml that had never been written. Subscribing means propose genuinely completes, the file exists, and the error message names a path that is really there.

§8.1What a confirmed row must carry

DecisionMeaningCompiles to a rule?
acceptthe top proposal is correctyes — and requires a rationale
remapa different variable is correctyes — requires an explicit variable
rejectthis column maps to nothingno — recorded in the audit trail
deferundecidedno — recorded in the audit trail

decisions.json carries every row, including rejects and defers — it is an audit trail, not a filtered work list (bin/confirm_ledger.py:20-25). Only accept and remap are actionable (:59).

Refusals 10–11 — stale, or unreasoned

Each row carries proposed_hash; a mismatch against the current ledger.proposed.yaml aborts with the diff, unless --allow_stale_ledger is set — in which case it proceeds with a loud warning naming every stale row (bin/confirm_ledger.py:113-158). Separately, with --require_rationale on (the default), an accept with an empty rationale is rejected at parse time (:117).

§8.2COMPILE_RULES — an id that survives a version bump

rule_id = rule_id_prefix + sha256(canonical_json({kind, from, to, params}))

The digest covers exactly those four fields (bin/compile_rules.py:90-92) — notably not rule_version, which is the pack's own version copied in from the pack YAML (harmonize.nf:831). A pack bump therefore changes every rule's rule_version and moves not one character of any rule_id, which is what makes a rerun after a pack bump diffable rather than mysterious.

Refusal (compile) — two rules, one target cell

Two different source columns compiling to the same (cohort, dataset, variable) is a defect, not a merge. With --fail_on_rule_collision on (the default), the run aborts naming both columns (bin/compile_rules.py:137-144). Silently picking one would make the output depend on rule ordering.

In this phase every compiled rule has kind: "column_map" (bin/compile_rules.py:84). The other three kinds the contract names — value_map, unit_convert, derive — belong to stages that do not exist yet.

The pattern worth naming

Eight of the eleven have no override at all. Of the three that do, two are numeric thresholds and the third shouts. There is no global --force, and — the load-bearing case — no flag anywhere that can satisfy refusal 9. A pipeline whose gates all have escape hatches has no gates.

§11.1Execution environment

All nine Python-backed processes run one digest-tagged image, docker.io/bolt3x/clinarmonize-duckdb:1.5.5_pyyaml6.0.2; only STAGE_OPEN_DATASET differs, on a digest-pinned ubuntu (harmonize.nf:429). One image across the whole run is one less thing whose version can drift between the baseline and a permuted replicate — which would show up as a leak that is really a packaging bug.

§12What this schematic does not cover

A schematic that states no limits reads as a claim of completeness. These are the real ones.

  • Five of the nine stages do not exist. link, map, derive, coverage, and emit are declared and gated, not implemented. Nothing in this document describes how a value is actually written into an OMOP table, because nothing does that yet.
  • The invariant claim covers propose only. ADR-003 scopes the harness to the proposer; the pipeline refuses any other --invariant_scope rather than honouring it. A proof verdict says the proposal ledger is outcome-blind. It says nothing about the four unbuilt stages downstream, where value mapping and endpoint derivation — both far easier places to leak — will live.
  • Provenance is designed, not built. The plan's second contract — every emitted cell resolving to (cohort_id, dataset_id, source_column, source_value, rule_id, rule_version) in a joinable provenance.parquet — has no implementing code in the tree. rule_id and rule_version exist; the table they would join into does not.
  • vocabulary is recorded, never resolved. The pack's pinned release string is read and written into versions.yml. There is no ATHENA download and no vocabulary lookup anywhere in the pipeline, so concept_id values are carried through as the pack supplies them — in the default pack, all zeros.
  • Only kind: column_map compiles. The three other rule kinds the contract names are unreachable, so a confirmed decision that logically implies a unit conversion currently compiles to a plain column mapping.
  • Single-machine assumptions are untested here. This document says nothing about executor profiles, resource labels beyond process_single, or how the harness behaves at 100 replicates on a scheduler rather than locally.
The honest summary

What exists today is a rigorously gated front half: read the data, describe it, propose mappings, prove the proposals did not peek at the outcome, and stop dead until a human signs off. The back half — the part that actually writes OMOP tables — is specified in the plan and absent from the code.
